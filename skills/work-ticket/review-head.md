# Review covers the PR head (RV-178)

A review covers a pull request only while the PR head is the commit the review read and its verdict is clean. A merge gate that binds the review to a commit rejects a report on any other head (Reeve parks it as `review-not-clean`, RV-1), and a person reading the report is misled the same way. Any push to the PR branch after the review moves the head past it: a fix of a review finding, a fix for PR feedback, a merge of the base branch, a rebase. `/ccmagic:auto-ticket` enforces this in its Step 4e and 4f; `/ccmagic:work-ticket`, `/ccmagic:pr-feedback`, and `/ccmagic:finish-ticket` follow this file when they run on their own.

**When it applies.** Standalone runs, interactive or autonomous. With `orchestrator:` in the grounding block, skip this file: the orchestrator reviews every pushed head itself and never finishes on a stale review. Never on a fix pass. The one exception is a push `/ccmagic:finish-ticket` makes itself (its conflict merge), which the orchestrator never sees: *Handle merge conflicts* in `skills/finish-ticket/merge-conflicts.md` says what an orchestrated finish does then.

## The check

Run it before the skill finishes or hands off, at the point its SKILL.md names, as separate Bash calls:

1. Read the PR head: `gh pr view {PR_NUMBER} --json headRefOid,headRefName` (the full 40-character `headRefOid` as GitHub reports it, never the local `git rev-parse HEAD`, which can differ from what the PR holds).
2. Find the commit the last review read, `reviewed_head`, and its verdict. Take the first of these that applies:
   - **A review of uncommitted changes in this run** (work-ticket's Step 5 review runs before the first commit) covers the first pushed head when that push committed exactly the changes it read, whatever its handshake `head:` says: that `head:` is the commit before the work, taken before the commit. So `reviewed_head` is the first pushed head, and work-ticket does not review the same changes twice. Any edit after the review (a fix of one of its findings included) leaves the head unreviewed.
   - **A review in this run** of committed code: its handshake `head:` (autonomous), or the `git rev-parse HEAD` run right before it started (interactive; review-ticket's Step 4 runs it with the diff, and for `/ccmagic:review` run it yourself first).
   - **A review posted on the PR** (what `/ccmagic:finish-ticket` reads when no review ran in this session): the newest comment whose first line is `# Ticket-Grounded Review:` (`gh pr view {PR_NUMBER} --json comments`), taken only from the login this run posts as (`gh api user --jq .login`), since anyone can post a comment with that heading. Its `reviewed_head` is the `head:` line in the fenced block that ends it; when that block has no `head:` (an interactive report), the full 40-character SHA the report names as the commit it read; when it names none, no review is found.

   The verdict is the handshake's `status:` (`clean`, `fixable-findings`, `needs-human`); for an interactive report with no handshake, `clean` means no introduced finding is left to fix.
3. The review covers the PR head only when `reviewed_head` equals the PR head **and** the verdict is `clean`: go on. A matching head with `fixable-findings` goes to step 4's fix loop; with `needs-human`, see *When the check fails*.
4. Otherwise, review the PR head again:
   - Make the checkout the PR head first, with a clean working tree and each command as its own Bash call: `git checkout {headRefName}`, `git fetch origin {headRefName}`, then `git merge --ff-only FETCH_HEAD`. Never a bare `git pull`: a branch pushed from a sandbox (Cyrus) has no upstream, since git cannot write `.git/config` there (`skills/push/SKILL.md`, *No upstream*), and a bare pull then fails as if the branch had diverged. A failed fetch is `reason: cannot fetch {headRefName} from origin: {first error line}`; a merge that cannot fast-forward is a real divergence, `reason: local branch has diverged from PR #{n}`. Either is a stop (autonomous: `needs-human`). Then confirm `git rev-parse HEAD` equals the PR head.
   - Run `/ccmagic:review-ticket` (with the autonomous grounding block in autonomous mode). When an earlier review exists, add `review_pass: {n}` (one more than the reviews so far in this run) and a `previous_findings:` section: the earlier report's findings, and one line per commit since it from `git log --format='- %h %s' {reviewed_head}..HEAD`, so the reviewer posts a delta report and reads each new commit's changes as new code.
   - Read the PR head again (step 1) and confirm that the new report's `head:` (interactively, the `git rev-parse HEAD` the review read) equals it.
   - `clean`: the review covers the PR head; go on. `fixable-findings`: in `/ccmagic:work-ticket` and `/ccmagic:pr-feedback`, fix the findings, push, and repeat from step 1 (the push moves the head again); `/ccmagic:finish-ticket` fixes nothing, so there it is a stop. `needs-human`: a stop.
5. Bound the fix loop by `max_review_fix_passes` (default 3, from `ccm-context`'s `config`): that many fix-and-review rounds after the first review, then a stop. A `fixable-findings` verdict with no round left is a stop, never a finish.

## When the check fails

- **Autonomous:** never finish, merge, or hand off on a stale review or on one that is not clean. A failed read of the PR head, a failed fetch, a diverged branch, a report whose `head:` is missing or differs from the PR head, `fixable-findings` with no round left (or in finish-ticket), or a `needs-human` review → `needs-human` with `reason: review covers {reviewed_head, 7 characters, or "no commit"} but PR #{n} head is {head, 7 characters}: {what stopped it}` (for a matching head that is not clean: `review of PR #{n} head {sha7} is {status}: {its reason}`). A top-level run does its own route-and-stop as its SKILL.md says.
- **Interactive:** say which commit the last review read, its verdict, and what the PR head is, and offer two options: review (and fix) the PR head now (step 4), or go on with the stale or unclean review, which the PR body or the final message then names (`Review covers {sha7}, not the PR head {sha7}.`). Never pick the second yourself.

## In /ccmagic:finish-ticket

Step 3d runs this check before Step 5b, the merge, or the hand-off, unless orchestrated (`/ccmagic:auto-ticket` reaches the finish step only with a clean review of the PR head, its Step 4e and 4f). It reads the posted review (step 2, third case) unless a review ran in this session. When the head differs or no review is found: autonomous, rerun `/ccmagic:review-ticket` on the PR head and confirm its `head:` and `status: clean`; interactive, offer that rerun or going on with the stale review named in the final message. In autonomous mode a review that is not clean on the PR head is a blocker like the merge gate's. The sanity check report gives the result on its `Review head:` line.
